# WidgetWarriors — Виджеты модулей на домашнем экране

## Цель

Дать пользователю выносить «живые» виджеты модулей SiE на домашний экран смартфона.
Виджеты должны:

- **выглядеть как часть приложения** — те же токены `SieColors`, те же скругления, типографика, акцентный цвет;
- **быть глубоко кастомизируемыми** — размер, тема, акцент, набор показываемых данных, фон;
- **оставаться минималистичными** — один-два ключевых показателя, никакого визуального шума;
- **работать офлайн** — данные читаются из локального Drift, без сети и без открытого приложения;
- **легко расширяться** — добавление виджета нового модуля = один Dart-провайдер + шаблонный нативный обвес.

Модули первой волны: **Планирование**, **Дыхательные практики**, **Фокусировка**, **Привычки**.

---

## Ключевое архитектурное решение

Android-виджеты (App Widgets) штатно рисуются через `RemoteViews` — ограниченный набор
вью, никаких кастомных painter'ов, градиентов и шрифтов приложения. Это несовместимо с
требованием «выглядеть как приложение».

**Решение: рендерим настоящие Flutter-виджеты в PNG** через пакет
[`home_widget`](https://pub.dev/packages/home_widget) (`HomeWidget.renderFlutterWidget`),
а нативный слой показывает картинку в одном `ImageView`. Поверх картинки кладём
прозрачные зоны-кнопки (`RemoteViews` + `PendingIntent`) для тапов и быстрых действий.

Плюсы:
- пиксель-в-пиксель тот же визуал, что и в приложении (переиспользуем `SieColors`, painter'ы);
- вся вёрстка — на Flutter, нативного UI-кода почти нет;
- единый конвейер рендера для всех модулей.

Минусы и как закрываем:
- картинка не интерактивна поэлементно → точки тапа делаем прозрачным overlay'ем `RemoteViews`;
- нужен перерендер при изменении данных → фоновое обновление (`WorkManager` + background-isolate);
- рендер в фоне требует headless-движка и read-доступа к Drift → см. `08-background-refresh-and-actions.md`.

## Принципы дизайна виджетов

1. **Один смысл на виджет.** Главное число/прогресс крупно, остальное — подпись.
2. **Тихий по умолчанию.** Фон `surface`/прозрачный, акцент только на ключевом элементе.
3. **Читается за 0.5 сек.** Кольцо прогресса, число, иконка модуля, короткий лейбл.
4. **Адаптивность размера.** Small (1×1/2×1), Medium (2×2/4×2), Large (4×2/4×3) — разный объём данных.
5. **Тема следует приложению**, но может быть переопределена на уровне инстанса виджета.
6. **Акцент наследуется из косметики** пользователя (equipped stat-style/background), если не задан вручную.

## Архитектура (слои)

```
┌─────────────────────────────────────────────────────────────┐
│ HOME SCREEN (Android launcher)                              │
│  ImageView(rendered PNG)  +  прозрачные tap-зоны RemoteViews │
└───────────────▲───────────────────────────┬─────────────────┘
                │ обновить                    │ PendingIntent (tap / action)
┌───────────────┴───────────────────────────▼─────────────────┐
│ NATIVE (Kotlin)                                              │
│  SieWidgetProvider (base) → PlanningWidget / FocusWidget …   │
│  SieWidgetBackgroundReceiver (быстрые действия)              │
└───────────────▲───────────────────────────┬─────────────────┘
                │ home_widget bridge          │ method channel / intent extras
┌───────────────┴───────────────────────────▼─────────────────┐
│ FLUTTER                                                      │
│  WidgetRegistry ──> ModuleWidgetProvider (по одному на модуль)│
│      ├─ dataLoader(db) -> WidgetData         (offline-first) │
│      ├─ render(ctx, config, data) -> Widget  (чистый UI)     │
│      └─ deepLinkRoute / quickActions                         │
│  WidgetRenderService  (фон + foreground, Flutter→PNG)        │
│  WidgetConfigStore    (per-instance config в SharedPrefs)    │
│  WidgetThemeBridge    (SieColors без ref, для headless)      │
└──────────────────────────────────────────────────────────────┘
```

**Сердце расширяемости — `WidgetRegistry`.** Каждый модуль регистрирует один
`ModuleWidgetProvider`. Конвейер рендера, конфиг-экран и фоновый воркер работают с
абстракцией и ничего не знают о конкретном модуле.

## Поток данных (offline-first)

1. Виджет/воркер просит `WidgetRenderService` обновить инстанс `appWidgetId`.
2. Сервис берёт `config` из `WidgetConfigStore` и `ModuleWidgetProvider` из реестра.
3. `provider.dataLoader(db)` читает **Drift напрямую** (без сети, без auth) → `WidgetData`.
4. `provider.render(ctx, config, data)` строит чистый Flutter-виджет.
5. `HomeWidget.renderFlutterWidget` → PNG в shared-папку, путь сохраняется в `HomeWidget`.
6. Native перечитывает картинку и перерисовывает `ImageView`.

Сеть нужна только приложению; виджеты живут на локальном зеркале Drift.

## Риски и открытые вопросы

- **Drift в background-isolate.** Один writer на SQLite. Для рефреша нужен только read —
  открываем отдельное read-соединение к тому же файлу. Проверить отсутствие блокировок.
- **Стоимость рендера.** PNG на каждый инстанс. Кэшировать по хэшу `config+data`, рендерить
  только при изменении.
- **Частота обновления.** `WorkManager` минимум 15 мин. Мгновенный апдейт — событийно из
  приложения (toggle привычки, конец фокус-сессии) через `HomeWidget.updateWidget`.
- **Шрифты в headless-рендере.** Приложение на системном шрифте — отдельная регистрация не
  нужна; если позже добавим кастомный шрифт, его надо явно прогружать в изоляте рендера.
- **`applicationId` = `com.example.central_hub`** — дефолтный. Не блокирует виджеты, но стоит
  учесть при будущем релизе в стор (вне рамок этой фичи).
- **Тема в момент рендера.** Headless-изолят не имеет `ProviderScope` → `SieColors` берём
  из `WidgetThemeBridge`, который читает `sie_theme_mode` напрямую из SharedPreferences.

## Критерии готовности (Definition of Done)

1. Виджет каждого из 4 модулей ставится на домашний экран и показывает реальные данные офлайн.
2. Тап по виджету открывает соответствующий экран модуля (deep-link через `rootNavigatorKey`).
3. Виджеты визуально неотличимы от карточек приложения (тема, акцент, скругления).
4. Экран «Студия виджетов» позволяет менять размер-вариант, тему, акцент и состав данных.
5. Данные обновляются: периодически (WorkManager) и событийно (из приложения).
6. Добавление пятого модуля по `09-extensibility-playbook.md` занимает < 1 дня и не трогает ядро.
