# План: Адаптация под масштаб экрана (пропорциональное масштабирование)

> **Цель:** Сделать так, чтобы UI выглядел пропорционально и не ломался при разном «масштабе экрана» (Screen zoom / Display size) и на устройствах с разной логической шириной — от узких (Samsung One UI с зумом, ~320–360dp) до широких (~430dp, планшеты, web).

**Режим:** Планирование → Реализация
**Стратегия (выбрана):** Пропорциональное масштабирование — глобальный коэффициент от ширины экрана относительно эталонной, применяемый к размерам через `.s`-хелпер.

---

## 1. Описание

### Корень проблемы
На Android два независимых параметра влияют на размеры:

| Параметр | Что меняет | Затрагивает |
|---|---|---|
| **Font size** (размер шрифта) | `MediaQuery.textScaler` | только текст |
| **Screen zoom** (масштаб экрана) | `devicePixelRatio` → **логическую ширину в dp** | весь layout |

В версии 2.7.60 уже добавлен кламп `textScaler` (макс 1.15×) — это закрывает только **шрифт**. Проблема пользователя (Samsung Galaxy S25) — увеличенный **масштаб экрана**: логическая ширина падает (напр. с ~390dp до ~320–350dp), и вёрстка, свёрстанная под одну эталонную ширину с фиксированными размерами, перестаёт помещаться (заголовки переносятся, ряды кнопок/чипов переполняются).

### Объём хардкода (замер по `apps/central_hub/lib`, 53 экрана)
- `fontSize:` — ~996
- `width:/height:` (числовые) — ~1910
- `SizedBox(width/height:)` — ~1204
- `EdgeInsets` — ~767
- `BorderRadius.circular(` — ~412

Плюс в `sie_core`: ~108 `fontSize`, ~57 `EdgeInsets`. Итого ~5000+ числовых литералов размеров.

### Почему «простой» путь не работает
Подмена `MediaQuery.size` в одном месте **не масштабирует layout**: большинство виджетов берут размеры из *constraints* родителя (реальная ширина `View`), а не из `MediaQuery.size`. `Scaffold`/`Expanded`/`Container` заполняют реальные constraints. Поэтому пропорциональное масштабирование требует, чтобы **сами размеры** (шрифты, отступы, фикс-ширины) проходили через коэффициент.

Root-`Transform.scale`/`FittedBox` поверх всего приложения формально масштабирует пиксели, но ломает: вьюпорты прокрутки, аспект, системные инсеты, и — критично для нас — **coach-mark overlay** (он смонтирован над навигатором в `MaterialApp.builder` и измеряет реальные render-box'ы; при root-трансформе подсветка разъедется). Поэтому этот путь отвергаем.

**Вывод:** идём по пути `.s`-хелпера (подход `flutter_screenutil`, но свой, в духе существующих токенов `SieColors`/`SieMotion`). Coach-marks при этом остаются корректными, т.к. они читают фактическую геометрию уже отмасштабированных виджетов.

## 2. Пользовательский сценарий

- На устройстве с эталонной шириной (~390dp) и обычным зумом — всё как сейчас (scale = 1.0, нулевая регрессия).
- На узком/зумленном экране (S25 с увеличенным Screen zoom, ~330dp) — весь UI пропорционально ужимается (scale ≈ 0.85): шрифты, отступы, кнопки, скругления уменьшаются согласованно. Заголовки не переносятся, ряды не переполняются. Выглядит как «то же приложение, чуть компактнее».
- На широком экране/планшете/web — UI не раздувается: scale капится на 1.0, а избыток ширины уходит в поля (уже есть `_webConstraint` maxWidth 560 для web; для широких телефонов scale=1.0 оставляет привычные поля).

## 3. Логика и поведение

### 3.1. Механизм `SieScale`
Новый токен в `packages/sie_core/lib/src/theme/sie_scale.dart` — в одном ряду с `SieColors`/`SieMotion`.

```dart
class SieScale {
  /// Эталонная ширина, под которую свёрстан дизайн.
  static const double referenceWidth = 390.0;
  /// Границы коэффициента: только вниз (не раздуваем на широких).
  static const double minFactor = 0.85;
  static const double maxFactor = 1.0;

  static double _factor = 1.0;

  /// Вызывается раз за кадр из MaterialApp.builder.
  static void update(double screenWidthDp) {
    _factor = (screenWidthDp / referenceWidth).clamp(minFactor, maxFactor);
  }

  static double get factor => _factor;
  static double s(num v) => v * _factor;
}

extension SieScaleNum on num {
  /// Масштабированный размер (шрифт/отступ/ширина/радиус).
  double get s => SieScale.s(this);
}
```

- Глобальное статическое состояние — как у `flutter_screenutil` (`ScreenUtil.init`). Для одно-оконного мобильного приложения приемлемо. (Открытый вопрос: InheritedWidget vs static — см. §6.)
- `SieScale.update(mq.size.shortestSide или size.width)` — вызывается в `_globalBuilder` до построения дерева.

### 3.2. Интеграция в `main.dart` (`_globalBuilder`)
В существующий `_globalBuilder` (где уже кламп textScaler) добавить:
```dart
final mq = MediaQuery.of(context);
SieScale.update(mq.size.width);
```
Порядок: сначала `SieScale.update`, затем строится контент. Текстовый кламп остаётся — итоговый размер текста = `baseFontSize.s * clampedTextScaler`.

### 3.3. Применение `.s`

> **Уточнение по ходу реализации (важно):** текст масштабируется **не** через `.s` на каждом `fontSize`, а **глобально** — домножением `MediaQuery.textScaler` на `SieScale.factor` в `_globalBuilder`. `textScaler` во Flutter применяется ко **всему** тексту (и темовому, и с явным `fontSize`), поэтому это покрывает 100% текста одним местом, без миграции ~996 литералов и без конфликтов с `const TextStyle`. Текст — главная причина переполнений, так что это и есть основной фикс.
>
> `.s` остаётся **только для нетекстовых размеров**, которые `textScaler` не трогает: иконки (`Icon(size:)`), фиксированные ширины/высоты контейнеров и кнопок, отступы, скругления. Их масштабируем точечно там, где это влияет на раскладку/переполнение (горизонтальные ряды с фикс-шириной), а не повсеместно.

Каждый нетекстовый числовой размер → `.s`:
```dart
fontSize: 22          →  fontSize: 22.s
SizedBox(height: 16)  →  SizedBox(height: 16.s)
EdgeInsets.all(20)    →  EdgeInsets.all(20.s)
BorderRadius.circular(16) → BorderRadius.circular(16.s)
width: 56             →  width: 56.s
```
- `letterSpacing` — тоже `.s` (узкие экраны особенно страдают от широкого трекинга).
- Иконки (`Icon(size: 18)`) — `.s`.
- НЕ масштабируем: `alpha`/прозрачности, доли (`0.0–1.0`), длительности анимаций (это `SieMotion`), `blurSigma` (опционально).

### 3.4. Фазы внедрения (чтобы не делать 5000 правок «вслепую» одним коммитом)

**Фаза 0 — инфраструктура (1 коммит):**
- `SieScale` + экспорт из `sie_core`.
- Интеграция в `_globalBuilder`.
- Юнит-проверка фактора на нескольких ширинах.
- На этом этапе визуально ничего не меняется (никто ещё не использует `.s`).

**Фаза 1 — «горячие» экраны (по приоритету реальных поломок):**
1. `habit_tracker_screen.dart` (шапка `_CyberTopBar`, карточки, нижняя панель)
2. `breathing_exercise_screen.dart`
3. `focus_protocol_screen.dart`
4. `operations_control_screen.dart` (хаб)
5. Общие виджеты `sie_core` (`SieGlassCard`, `SectionHeader`, карточки, `CoachMarkOverlay` карточка)

**Фаза 2 — остальные 48 экранов** пакетами по модулям (planning, garage, leaderboard, profile, knowledge base, meditation, dev studio и т.д.).

**Фаза 3 — домашние виджеты** (`widgets_home/`) — отдельная подсистема (рендер в битмап), масштабируется от размера слота, не от экрана. Возможно, свой коэффициент. (Связано со скрином с обрезанными чипами.)

### 3.5. Ускорение миграции (codemod)
Полу-автоматизация регуляркой для самых частых безопасных паттернов, затем ручной ревью каждого файла:
- `fontSize: <num>` → `fontSize: <num>.s`
- `SizedBox(height: <num>` / `width: <num>` → `.s`
- `EdgeInsets.all(<num>)`, `.symmetric(...)`, `.fromLTRB(...)`, `.only(...)` → обернуть каждое число `.s`
- `BorderRadius.circular(<num>)` → `.s`

> **Важно:** codemod только готовит диф, **каждый файл ревьюится вручную** — есть случаи, где число не размер (индексы, count, флаги, `ValueKey`, длительности). `replace_all` вслепую запрещён.

### 3.6. Контроль качества
- После каждой фазы: `flutter analyze` (0 ошибок) + сборка.
- Визуальная проверка на 3 виртуальных ширинах (узкая 320, эталон 390, широкая 430) — через DevicePreview или ручной resize.
- Регрессия эталона: при scale=1.0 пиксель-в-пиксель как до миграции.

## 6. Открытые вопросы

1. **Эталонная ширина** `referenceWidth`: 390dp (Pixel-класс) — подтверждаем, или подобрать под конкретное устройство, где дизайн «канонично» выглядит? От этого зависит, будет ли на большинстве телефонов scale = 1.0.
2. **Границы фактора:** только вниз `[0.85, 1.0]` (рекомендую — не раздуваем широкие экраны), или разрешить лёгкий рост до ~1.1 на широких? И насколько низко пускать (0.85 vs 0.80) — компромисс «помещается» против «читаемо».
3. **База фактора:** `size.width` (рекомендую — переполнение по горизонтали) или `shortestSide` (стабильнее в ландшафте)?
4. **State хранения фактора:** статик (как screenutil, проще, но глобальное состояние) или `InheritedWidget`/Riverpod-провайдер с `.s(context)` (чище, но многословнее в вызовах)?
5. **Текстовый кламп:** оставляем текущий `textScaler` 1.15× поверх `.s` (рекомендую) — итог `fontSize.s * textScaler`. Не получится ли «двойного» уменьшения на узком+мелкий шрифт? Возможно, пересмотреть верхнюю границу.
6. **Планшеты/ландшафт/web:** на широких scale=1.0 + текущий `_webConstraint` (maxWidth 560). Достаточно, или нужен отдельный «планшетный» режим (2 колонки и т.п.) — вне этого плана?
7. **Домашние виджеты (Фаза 3):** масштабировать от размера слота виджета, а не от экрана — отдельный коэффициент. Брать ли в этот план или вынести (там же баг с обрезкой чипов)?
8. **Объём за раз:** делать фазами с отдельными коммитами/APK на проверку после Фазы 1 (рекомендую), или гнать всё до конца перед первой проверкой?

## 7. Что НЕ входит (отдельные задачи)
- **Сфера дыхания** — GLSL-шейдер не рендерится на GPU S25 (мраморный фолбэк). Нужен не-шейдерный фолбэк-рендер. Отдельно.
- **Обрезка чипов в домашнем виджете** — связана с Фазой 3, но корень — рендер битмапа под слот; может потребовать своего разбора.
