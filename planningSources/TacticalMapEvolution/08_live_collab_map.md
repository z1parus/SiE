# Этап 8 — Живой совместный холст (real-time)

## Описание

Капстоун коллаборации: превращает карту в **живое многопользовательское рабочее пространство**.
Участники, открывшие одну цель одновременно, видят **курсоры друг друга**, **перемещения узлов и
элементов в реальном времени** и **кто что сейчас редактирует** — как в Figma/Miro.

База уже есть: канал **Supabase Realtime Presence `goal_presence:{goalId}`** (онлайн-индикаторы,
`mission_detail_screen.dart:40-70`) и цветовая кодировка участников (этап 5). Этот этап надстраивает
над ними **broadcast эфемерных событий** (курсоры, перетаскивания) — без новой персистентной схемы.

Зависит от этапа 1 (есть что двигать — map-элементы) и этапа 5 (цвета/идентичность участников).

## Пользовательский сценарий

1. Алиса и Боб открыли одну совместную цель в режиме карты. В углу — аватары онлайн-участников
   (presence уже есть).
2. Алиса видит **курсор Боба** (стрелка его цветом + имя), двигающийся по холсту в реальном времени.
3. Боб перетаскивает узел — Алиса видит **плавное перемещение** почти мгновенно (broadcast), а не
   только после сохранения.
4. Пока Боб редактирует узел/заметку — у Алисы он помечен «🔒 Боб редактирует» (мягкая блокировка,
   предупреждение о конфликте, не жёсткий лок).
5. Кнопка **«Следовать за …»** — камера Алисы повторяет вьюпорт выбранного участника (режим
   презентации/ревью).

## Логика и поведение

### Транспорт
- Расширить существующий канал `goal_presence:{goalId}` (или добавить parallel broadcast-канал
  `goal_map:{goalId}`) на **broadcast-события** Supabase Realtime:
  - `cursor` — `{userId, x, y}` (логические координаты), throttle ~20–30 fps, отправляется только
    при движении.
  - `node_move` — `{userId, nodeId, x, y}` во время drag (throttle), и финальный — через обычный
    `saveMapPositions` (источник истины — БД).
  - `editing` — `{userId, nodeId, active}` при открытии/закрытии редактирования узла/элемента.
- Всё **эфемерно** (broadcast, не БД): при оффлайне просто нет live-слоя, данные не теряются.

### Рендер
- Новый слой `_LiveCursorsLayer` (в `_repaint`-Stack, поверх всего): курсоры участников их цветом
  (`memberColor`, этап 5) + подпись-имя; плавная интерполяция позиций между событиями (Tween).
- «Призрачное» перемещение: при `node_move` от другого участника — обновлять его представление узла
  с лёгкой задержкой/прозрачностью, пока не придёт финальный сейв.
- Бейдж «редактируется» на узле (иконка + цвет участника).

### Конфликты
- Мягкая блокировка: `editing`-событие показывает предупреждение, но **не** запрещает (last-write-wins
  по `updated_at`, как и сейчас). Жёсткий лок — открытый вопрос.
- Источник истины — всегда БД; broadcast лишь сглаживает UX между сохранениями.

### Edge cases
- **Оффлайн/слабая сеть** — live-слой деградирует молча; план-данные не зависят от broadcast.
- **Много участников** — клампить частоту/число отрисованных курсоров; throttle/debounce.
- **Уход участника** — presence `leave` убирает его курсор/бейджи.
- **Производительность** — курсоры в отдельном лёгком слое; интерполяция через единый
  `AnimationController`, не per-cursor таймеры.
- **Приватность** — транслируются только координаты/ID в пределах участников цели (RLS канала по
  membership).

## Схема данных

Персистентных таблиц нет. Эфемерные payload-форматы broadcast:
```jsonc
// channel: goal_map:{goalId}
{ "type": "cursor",  "userId": "...", "x": 1234.5, "y": -200.0 }
{ "type": "node_move","userId": "...", "nodeId": "node:uuid", "x": 1100, "y": 50 }
{ "type": "editing", "userId": "...", "nodeId": "el:uuid", "active": true }
```

## Открытые вопросы

1. **Жёсткая блокировка при редактировании** vs мягкое предупреждение. Рекомендация: мягкое (как
   сейчас last-write-wins); жёсткий лок — сложнее и спорнее по UX.
2. **Отдельный broadcast-канал** `goal_map:{goalId}` vs расширение `goal_presence`. Рекомендация:
   отдельный канал (чище разделение presence/broadcast, меньше шума в presence-стейте).
3. **Лимит частоты/масштабируемость** Realtime. Рекомендация: throttle курсора ~30 мс, node_move
   ~50 мс; мониторить нагрузку, при необходимости — адаптивный throttle от числа участников.
4. **Нужен ли live для личных целей.** Нет — фича включается только при наличии accepted-коллабораторов.
5. **Порядок внедрения относительно этапа 5.** Делать строго после 5 (цвета/идентичность участников
   обязательны для курсоров).
