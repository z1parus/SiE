# Этап 3 — Карточки-изображения и референс-доска на холсте

## Описание

Свободные **карточки-изображения**, размещаемые прямо на холсте карты как самостоятельные объекты —
**только карта-нативные** (в списке их нет). Это превращает тактическую карту в **мудборд /
референс-доску**: скриншоты-вдохновение, диаграммы, фото-наброски, вырезки — рядом с деревом цели,
для работы над целью именно в визуальном режиме.

Отличие от этапа 2: вложения этапа 2 **привязаны к узлу** и видны в списке; карточки этого этапа —
**свободные объекты холста**, не принадлежат ни одному узлу плана, существуют только на карте.

Технически это **частный случай `MapElement` с `kind = image`** из этапа 1 — отдельная таблица не
нужна, переиспользуется `goal_map_elements` (поле `media_url`) и Storage-бакет `goal-media` из
этапа 2.

## Пользовательский сценарий

1. В палитре режима редактирования (этап 1) — инструмент **«🖼 Изображение»**.
2. Тап → выбор изображения (`image_picker`) → загрузка в `goal-media` → на холсте появляется
   карточка с изображением в точке тапа.
3. Карточку можно **перетаскивать**, **менять размер** (угловой хэндл, сохраняя пропорции),
   удалять; опц. подпись снизу (`content`).
4. Карточки рисуются **под узлами** (фоновый слой по `z_index`), чтобы не перекрывать дерево цели —
   как «обои/референсы» рабочего пространства.
5. В списочном режиме — отсутствуют.

## Логика и поведение

### Переиспользование этапа 1
- Никаких новых таблиц/моделей: `MapElement(kind: image, mediaUrl: ..., w, h, content?)`.
- CRUD — те же `addMapElement`/`updateMapElement`/`deleteMapElement`/`saveMapElementPosition`.
- Sync-op — тот же `upsert_map_element`/`delete_map_element`.

### Загрузка изображения
- Тот же путь, что вложения (этап 2): `storage.from('goal-media').uploadBinary(...)` → `media_url`.
- Офлайн — `local_path` в записи элемента + sync-op догрузки (как этап 2).

### Рендер и слой
- Новый виджет `_ImageCardElement`: `Positioned` по `_cx + pos`, `cached_network_image`, рамка
  `c.flatCard`, опц. подпись.
- Слой изображений размещается **под** `_EdgePainter`/узлами (фон), по `z_index`. Заметки (этап 1) —
  над узлами. Порядок слоёв задаётся в `_repaint`-Stack.
- Resize: угловой хэндл, сохранение пропорций (`w/h` из intrinsic ratio), min-размер; debounce-сейв.

### Edge cases
- **Тяжёлые изображения** — сжатие при выборе (как этап 2); ленивая загрузка вне видимой области
  холста (можно отложить — холст и так в `_repaint`).
- **Карточка без изображения** (отмена выбора) — не создавать элемент.
- **Перекрытие узлов** — изображения всегда под узлами по `z_index`; пользователь двигает их свободно.
- **Viewer** — видит карточки, не редактирует.
- **Производительность большого мудборда** — ограничить число одновременно декодируемых
  изображений; `cacheWidth` для миниатюр на холсте при малом зуме.

## Схема данных

Без новых таблиц. Используется существующая `goal_map_elements`:
```
kind     = 'image'
media_url= <публичный/подписанный URL из goal-media>
w, h     = размеры карточки на холсте (логические)
content  = опциональная подпись
z_index  < z_index узлов (фоновый слой)
```

## Открытые вопросы

1. **Слой: строго под узлами или свободный z-order.** Рекомендация: в MVP — фоновый слой (под
   узлами), это закрывает кейс «референсы-обои». Свободный z-order («на передний план») — позже,
   общий для всех `MapElement`.
2. **Вставка из буфера/ссылки.** Рекомендация: MVP — только `image_picker`; вставка по URL/из
   буфера — расширение.
3. **Совместное использование Storage-квоты.** Рекомендация: считать карточки и вложения в общий
   лимит цели; задать мягкий предел числа изображений на цель.
4. **Кроп/поворот.** Рекомендация: вне MVP; при необходимости — отдельный мини-редактор.
